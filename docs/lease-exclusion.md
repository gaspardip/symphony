# Local lease mutation exclusion

`LeaseManager.acquire/4`, `refresh/3`, and `release/2` serialize their read/decision/write sequences through an atomic `mkdir` of `<lease path>.lock`. This works across independent BEAM processes that share the same local filesystem store. Each call waits at most approximately one second for an occupied critical section before returning `{:error, {:lease_lock_timeout, lock_path}}`; filesystem setup failures return `{:error, {:lease_lock_failed, lock_path, reason}}`. Callers must not treat these results as acquired or released ownership.

The call which creates the directory removes it when its operation returns or raises. It never removes another call's existing directory, never uses the lease TTL to steal a lock, and never automatically clears an orphan. If a process is killed during this critical section, the remaining directory deliberately prevents further mutation. Diagnosis identifies its path; recovery requires inspection and an explicit operational decision after confirming the holder is no longer active. This is a fail-closed interruption outcome, not automatic crash recovery. Failure to release a created lock raises an explicit filesystem error.

For ordinary, audit-complete leases, TTL, epoch increments, owner comparison and timestamp normalization remain unchanged. `read/1` rejects valid JSON which is not an object as `:invalid_lease`. `release/2`, including the ownerless form, now returns an error for unreadable or invalid JSON instead of acknowledging a no-op or deleting corrupt evidence. It preserves the file in those cases. An incorrect owner on a valid lease remains a no-op, a missing lease remains `:ok`, and actual deletion errors are returned. Malformed timestamps retain their existing behavior; this change is not full schema validation of legacy leases.

The critical-section lock protects metadata decisions only. It does not stop a worker which has lost ownership, fence external side effects, or provide exactly-once execution across hosts. All mutating participants must run the same locking protocol and use the same store; old binaries, direct file writers and network filesystems are outside the tested guarantee. A higher-level caller may still explicitly force release a valid, audit-complete lease using `release(issue_id)`. Ownerless release cannot remove pending or unreadable audit evidence.

`elixir/test/symphony_elixir/lease_concurrency_test.exs` exercises simultaneous acquire in three clean rounds, release versus takeover, and refresh versus takeover using distinct OS/BEAM processes behind a shared start barrier. It also verifies that a foreign/orphaned lock remains untouched, setup errors block mutation, and invalid JSON/non-map payloads are preserved. The invalid-JSON release assertion now requires an error while retaining its byte-preservation assertion. Test results must be recorded from the actual source cut; writing these tests alone does not establish PB-04/CR-09 acceptance or a video.

## Audited stale-lease takeover

Initial acquisition and ordinary refresh retain their existing behavior. Taking ownership from a stale, different owner uses a checked intent/confirmation sequence under the same lease lock:

1. Prepare `lease.takeover.requested` and `lease.taken_over` once, with one operation ID and distinct stable event IDs.
2. Persist the intent through `RunLedger.persist_prepared/1`. If this fails, leave the previous lease untouched.
3. Write the candidate lease with `audit_pending`, including the previous lease, ledger path, intent ID and exact prepared confirmation.
4. Persist `lease.taken_over` only after that candidate is on disk.
5. Remove `audit_pending` through the existing atomic JSON replacement and only then return `:ok` from acquisition.

The confirmation describes the ownership change recorded on disk; it does not prove worker execution. Intent, lease-write, confirmation and finalization failures return `{:error, {:lease_takeover_failed, phase, operation_id, reason}}`. Configuration/preparation failures retain the checked ledger error. A failure after the pending candidate is written leaves that candidate visible for diagnosis and never automatically restores or deletes the previous owner's data.

`read/1`, `acquire/4`, `refresh/3` and `release/2` return `{:error, {:lease_audit_pending, operation_id}}` for a pending lease. An invalid pending shape returns `:invalid_lease_audit_pending`. Such leases are not reclaimable even after their TTL; callers must not treat any of these errors as ownership or release. Acquisition already gates new-worker creation on `:ok`. The lease module itself does not stop a running worker; the refresh contract below defines the orchestrator action for these errors.

`reconcile_pending_takeover/1` is an explicit operation, never a side effect of read. It removes pending only when the configured ledger path still matches the stored path, the candidate owner/epoch/digests match its prepared confirmation, and the complete checked ledger contains the matching intent and exact confirmation. It does not append a missing event, regenerate an identity or retry a failed write. Missing, corrupt, duplicate or inconsistent evidence returns an error and preserves the pending file. Reconciliation uses the same filesystem lock, so a lock orphaned by an abrupt process death remains a blocker requiring separate inspection and an explicit operational decision. This API does not authorize deleting an orphaned lock.

The new `lease_takeover_audit_test.exs` covers success ordering, unchanged initial acquisition/refresh, corrupt-ledger dispatch rejection, real filesystem obstructions at each write boundary, pending mutation denial, exact reconciliation and corrupt-evidence preservation. The separate local candidate harness also tested independent BEAM contenders against a stale lease and a persisted pending lease. These are local filesystem results, not a power-loss guarantee or distributed transaction: the lease replacement does not add directory fsync, and legacy ledger writers remain outside the checked-writer protocol. Closing this boundary does not establish global PB10 acceptance.

## Uncertain ownership of a running worker

`Orchestrator.refresh_runtime_config/1` stops the local worker for four refresh errors: `{:lease_audit_pending, operation_id}`, `:invalid_lease_audit_pending`, `%Jason.DecodeError{}`, and `:invalid_lease`. It cancels the automatic retry timer, requests task termination and waits for the worker's DOWN notification. Only after termination is confirmed does it remove the original monitor and running entry. It retains the claim, lease bytes, snapshot, workspace and dispatch journal, and reports `{:lease_ownership_uncertain, issue_id, reason}`. If termination cannot be confirmed, it retains the running entry with its uncertainty reason and includes the termination error in the diagnostic. A late DOWN retires only the running entry and updates local totals; it cannot finish the journal, release the claim or schedule a retry. Repeated stop requests and later renewal checks preserve this decision even if the lease file has since been repaired.

This path does not call `DispatchAudit.finish`, release the lease, alter the snapshot or schedule retry. A late original DOWN cannot retire the journal because the running entry was removed only after confirmed termination. The preserved journal blocks fresh dispatch. Diagnosis and explicit recovery remain necessary; stopping the local task does not cancel an external operation already sent to a provider.

Healthy renewal continues to synchronize the lease while keeping the same worker. Existing `:claimed` and `:missing` handling remains unchanged. Filesystem and lock errors such as `:eisdir` retain their existing warning-and-continue behavior. That compatibility choice is not a claim that every filesystem error is safe indefinitely, and this change adds no general fencing timeout.

The local candidate checks comprise 13 takeover tests and six refresh integration tests. The latter use real LeaseManager, DispatchGate and TaskSupervisor code with a controlled worker: four corruption/pending cases, healthy renewal, and the existing `:eisdir` behavior. They verify DOWN, cancelled retry, retained claim, unchanged lease/journal/snapshot/ledger bytes, and denial of a fresh dispatch. Two further real-process regressions cover an unconfirmed stop followed by late DOWN, and healthy renewal followed by repeated stop. The final integrated source passed 1,222 tests with 81.38% coverage and the configured lint, types, build and harness checks. PB05 passed its unchanged 60 checks across three two-VM repetitions on frozen source/BEAMs. A 100 ms concurrency-message timeout in an earlier full run remains a recorded observation; its exact cause was not confirmed, its test was unchanged, and both the focused and full reruns passed. See the checkpoint details in `.symphony/progress/PB10-lease-audit.md`; these local results do not establish global PB10 or real-service acceptance.
